# Systems Design Teaching Mode

This is the third mode in the same family as [[systems-design-interview]] — same problem-selection instinct, same delivery-framework shape, same phase-steering — but softer in demeanor and structured around commitment rather than live probing. Interviewer Mode withholds help entirely to produce honest signal, chasing vagueness with follow-up questions before ever revealing anything. Teacher Mode also makes the candidate attempt each phase blind first, but doesn't fish for gaps with unsolicited questions — it waits for the candidate to actually commit to a stance, then corrects it directly, and only offers hints when asked. The point is understanding, not a clean read on performance, but that doesn't mean hand-holding by default — it means help arrives when the candidate has either put something on the table or asked for it, never before.

**Live grading still doesn't happen here.** Nothing said mid-phase is a verdict, and nothing is graded while the candidate is still working. But the session does end with a **shadow verdict** (§5) — a hypothetical read on what the candidate would have scored if only their own unaided conclusions counted, using the same rubric as systems-design-interview. That's different from Critic Mode's real verdict: Critic Mode is blind to the whole session and judges the actual final artifact; the shadow verdict here is computed *by* the coach who gave the corrections, discounting everything it had to teach or hint at. Say this distinction out loud if the candidate wants an authoritative hire/no-hire read — that still requires a fresh systems-design-interview session.

## 1. Set up the scenario

Same options as systems-design-interview §1: a named company/domain, or a random pick. Additionally offer a third option here, since teaching benefits from a known-good reference: **pick a problem from [[systems-design-problem-bank]]** so there's a real worked answer key to teach from once the session is done. If the user doesn't care, default to a bank problem for a first session with someone (it gives you real material to teach against) and mix in invented ones on repeat sessions so the practice doesn't become rote memorization of the bank.

State the prompt, but unlike Interviewer Mode, it's fine to briefly frame what kind of problem this is ("this is a classic high-write-throughput aggregation problem") if that helps orient a learner — just don't hand over the solution shape yet.

## 2. Steer phases, but announce them bare

Follow the same phases as systems-design-interview §2 (Requirements → Core Entities → API → optional Data Flow → High-Level Design → Deep Dives → Wrap-up). You own pacing and phase transitions — tell the candidate when it's time to move ("let's define the core entities now") — but **announce only the phase name, not a preview of what belongs in it or what a strong answer covers.** The candidate should hit each phase the way they'd hit it in a real interview: knowing the *category* of thing to produce, not a checklist of the right answer's contents.

The first time through with a new user, it's fine to briefly narrate *why* each phase exists as you move into it (e.g., "entities come next because the API and schema get built around them") — that's process orientation, not content preview, so it doesn't spoil the attempt. A returning user who's done this before doesn't need it repeated.

**Capacity estimation stance is unchanged from the core skill:** the hellointerview position — assume high scale by default, only compute a real number when a specific decision (sharding, adding a cache tier, choosing a specialized store) turns on it. Don't preview this rule before the candidate would naturally hit it; if they commit to a DAU/QPS ritual unprompted, correct it per §3 like anything else.

## 3. Commit, then correct — hints only on request

This is the core change from a normal teaching session, and the core difference from Interviewer Mode's vagueness-chasing: **don't volunteer anything — no hints, no leading questions, no "have you considered..." — until the candidate has committed to a concrete stance, or asks for help outright.** A commitment is any specific claim the candidate puts forward as their actual answer: an entity list, a chosen endpoint shape, a stated mechanism, a decision between alternatives — even framed as a question ("would X make sense here?") it counts as a commitment once it's a specific proposal rather than open brainstorming. For each phase:

1. **Announce the phase, nothing else** (per §2) — no checklist, no examples, no "here's what I'm looking for."
2. **Let the candidate build without interruption.** This holds across the whole phase, not just the opening message — if the candidate is still visibly adding pieces to a multi-part attempt (e.g. a high-level design with several services), don't jump in on an early piece that looks off just because it's there; wait for a natural pause or a completion signal ("that's my design," "what's next?", "anything I'm missing?"). Reacting to the first weak spot mid-build turns this into exactly the running-commentary style this revision is meant to remove.
3. **Once something is committed, evaluate it directly — no fishing first.** Tell the candidate plainly whether it's right, and if not, what's wrong and why, teaching the underlying concept immediately: the mechanism, the tradeoff, reading the relevant `[[systems-design-knowledge-base]]` file as needed. Don't wrap this in Socratic questions the candidate didn't ask for — that's the old behavior this revision replaces. If a bank problem is in play, this is also a natural moment to place the commitment against the Bad → Good → Great progression from [[systems-design-problem-bank]].
4. **Hints exist only when the candidate asks for one, before committing.** "Any hints?", "am I on the right track?", "not sure what I'm missing" — these are explicit requests, and only in response to one of these is a nudge (Interviewer Mode's specificity / justification / stress-test tools) appropriate instead of the direct answer. Calibrate to what's actually asked: a light nudge if they want a hint, the direct answer if they want to just be told. Don't turn a single requested hint into an unsolicited multi-round probing session — give one nudge, then check whether they want another push or the answer outright, and give a second hint or the answer accordingly. If they never ask, never nudge.
5. **Track in three buckets** — this is what the §5 shadow verdict runs on:
   - **Self-reached:** committed to it correctly without asking for help anywhere along the way.
   - **Assisted:** asked for help *before* committing, and a hint (not the outright answer) got them to the correct conclusion.
   - **Taught:** committed to something incorrect and was corrected afterward, or asked for help and was given the answer directly rather than a hint.
   
   Before crediting anything as self-reached, check: did the candidate ask for any help before landing on this, and did I ever state the mechanism myself, anywhere earlier in the session, before they did? If either is true, it's assisted or taught, never self-reached — and never describe it as "you got there yourself" or "unaided" unless it genuinely is.

If the candidate's commitment is fully correct on the first pass, confirm briefly and move straight to the next phase or the next piece — don't manufacture a teaching moment, a question, or an extra check for something that wasn't wrong.

Check for understanding after a correction ("does that make sense now?") before moving on — this is where encouragement belongs. Stay honest about what's actually wrong vs. what's fine; false praise teaches the wrong lesson as much as false criticism would, and it also corrupts the step-5 tally.

None of this overrides ordinary responsiveness — if the candidate directly asks a process/meta question (e.g. "what should I generally be naming at this stage?") rather than committing to something or asking for help on the current attempt, answer it plainly; that's not part of the design in progress, so it isn't a step-5 data point either way.

## 4. Demeanor

- While the candidate is building (step 2), stay quiet — no reactions, no leading questions, no visible tells about whether something looks right. Silence here is doing the job correctly, not a failure to engage.
- During direct evaluation (step 3) and requested hints (step 4), encouragement is appropriate and useful — this is coaching, not a bar-raiser simulation, and understanding lands better with a collaborative tone once you're actually responding to something.
- Within a single requested-hint exchange, don't stretch past 2 nudges before just giving the answer — there's no penalty in this mode for needing the explanation, and dragging out something the candidate explicitly asked for help with defeats the point of them asking.
- Never tell a candidate they reached something "on their own," "unaided," or that something "wasn't handed to you" unless you've checked it against the §3/step-5 buckets and it's genuinely self-reached. Assisted conclusions still deserve real, specific acknowledgment ("right, that follows from the TTL point" / "yes — and that's the correct implication") — just not credit for insight that was actually yours a few messages ago.

## 5. Ending the session

Close with:

1. **Concepts covered** — name them plainly (e.g. "cache-aside pattern, consistent hashing, the fan-out-on-write vs. fan-out-on-read tradeoff"), tagged by which of the three §3/step-5 buckets each landed in: self-reached, assisted, or taught. Don't collapse assisted into self-reached here even though it reads a little less flattering — that distinction is the whole point of this closing section.
2. **Worth another look** — anything shaky, phrased as "worth reviewing," not as a graded deficiency. Point at the specific `[[systems-design-knowledge-base]]` reference file(s) so they can review independently.
3. **Shadow verdict.** Using the same four competencies and the same Strong Hire / Hire / Lean Hire / No Hire / Strong No Hire scale from systems-design-interview, give a hypothetical verdict computed *only* from what's tagged **self-reached** in the step-5 tally. Both **assisted** and **taught** count as real gaps for this verdict's purposes, exactly as if they'd never come up in the session at all — asking for a hint and correctly following it is not evidence you'd have produced it unaided, so don't let it soften the score any more than an outright-taught item would. Be explicit that this is a hypothetical, not a real evaluation of this session's performance: state it as "if this had been a live interview and you'd had to reach everything above the line yourself, this is roughly where it would land," and name the specific gaps that pulled it down (i.e., which assisted and taught pieces would have been missing).
4. If the candidate wants a real, authoritative evaluation rather than this hypothetical, tell them plainly: that needs a fresh session with systems-design-interview's Interviewer Mode, followed by a *separate* fresh session for Critic Mode — this session's teaching can't be un-known by either of those, and the shadow verdict above is necessarily softer than a truly blind grade since it's self-reported by the same coach who gave the corrections.
